# Aquarium（水族箱）设计文档 v0.3

> 一个运行在 QQ 上、**真正好用**、**像真人一样互动**的 AI 群友 bot（可多个）。
>
> 项目名：**Aquarium / 水族箱**——养几条会“水群”的鱼：有情绪、会睡觉、彼此互动，大家隔着玻璃看它们。（曾用临时名 QQ-Bond）
> 做得开心为先，不强求赶秋招；Agent 相关的设计点顺带可作面试素材。
> 记录 2026-10-11 ~ 10-12 设计拷问（Q1–Q20）的全部决策，作为编码依据。改决策先改这里。
> 生态调研见同目录 `RESEARCH-qqnt-ecosystem.md`。
>
> v0.2：可用模型与默认槽位（§8）、预算估算（§11）。
> v0.3：多账号；群友画像（成分标签 + 关系）；会话点选；离线补课；四种活跃模式；人设库；情绪与好感度；私密信息分级；bot 之间的互动；存档与回档；重新切分阶段。

## 1. 定位与原则

- **核心**：AI 群友。群里的人都知道它们是 bot（会公开告知、群名片可带标识）；“像真人”指的是说话方式和互动方式，不是冒充人类。
- 使用场景：**亲密朋友群**。
- 原则：
  1. 所有设置任何时候都可改、热重载、可删除（根治 Tulpa 痛点）。
  2. 所有内部状态（标签、情绪、好感度、私密信息等级、决策理由）**只在控制台可见，绝不暴露给群友**。
  3. 宁可不说，也不说错（尤其涉及私密信息）。

## 2. 运行环境与进程模型

### 2.1 运行环境
- 用户自己的 **Windows** 电脑。开机静默启动，托盘图标（状态 / 打开控制台 / 重启 / 退出），无窗口。

### 2.2 进程托管（N 个账号）
```
QQ.exe(账号1) ┐
QQ.exe(账号2) ┼←注入─ SnowLuma（无窗口） ←OneBot v11 WS（每账号一条）─ Aquarium（主进程，托盘）
QQ.exe(账号N) ┘
```
- Aquarium 是唯一入口，作为 supervisor 拉起并监控所有 QQ 实例与 SnowLuma。
- **架构一开始就按 N 个账号设计**，实现上先跑通 1 个。
- 默认：bot 全包（拉起 QQ → SnowLuma → 连接）；QQ 需要扫码 / 验证时托盘变色 + 通知，进入等待态。
- 健康检查：子进程退出自动重启（指数退避）；WS 断线重连（1s→30s）；断线时挂起的请求全部 reject。
- **检测 QQ 版本**，变化时告警（QQ 更新导致注入失效是最常见故障）；建议锁定版本、关闭自动更新。

### 2.3 只接入 bot 账号，绝不碰主号
- SnowLuma 默认 `hookAutoLoad = false`，WebUI 提供 `POST /api/processes/:pid/load`。
- bot 自己启动每个账号的 QQ.exe → 记录 PID → 只注入这些 PID → 连接后校验登录 QQ 号与配置一致，不一致拒绝工作并告警。

### 2.4 适配层
- 内部定义自己的事件 / 动作模型；**先实现 OneBot v11 适配器**；以后可加 Milky / Satori 适配器而不改核心。

## 3. 技术栈

- **TypeScript**，运行时优先 **Bun**（单 exe）；`@snowluma/sdk` 不兼容则退回 Node 22+。第一步 spike 验证。
- 存储：SQLite（消息、档案、记忆、情绪、用量）+ 配置文件（TOML/YAML）+ 人设 Markdown。
- 控制台：同仓库前端，由 bot 本地 HTTP 服务托管；**只监听 127.0.0.1，必须设密码**。
- 存档：isomorphic-git（纯 JS，用户无需安装 git）。

## 4. 账号、人设与会话

### 4.1 账号 ↔ 人设
- **每个账号绑定一个人设**，有自己的记忆、情绪、对每个人的好感度。
- **人设库**：控制台管理多个人设卡；支持**导入 Markdown 人设**（尽量兼容 Tulpa / ai-bot-groupmate 的人设格式）；编辑 + 预览，改完立即生效。
- 人设卡：身份 / 说话风格 / 禁忌 / 示例对话；每个会话可叠加“在这个群里的补充说明”。

### 4.2 会话
- 统一会话模型：每个群、每个私聊对象都是一个 `Session`，群聊私聊同一条管线。
- **会话点选**：控制台直接从 QQ 拉取该账号的群列表、好友列表、最近会话（`get_group_list` / `get_friend_list` / `get_recent_contact`），**勾选哪些会话启用**。这就是白名单界面；未勾选的会话一律不回。
- 配置两层继承：`全局默认 → 单会话覆盖`，标出继承 / 覆盖，可一键重置。
- 自动产生的数据与用户配置分开存储；配置写入原子化。

### 4.3 离线补课（重启时）
- **读**：拉取离线期间所有 @ 或提到自己的消息，加上最近一段消息（按时间窗口和条数**取较小值**），用于更新上下文与记忆。
- **回**：只回应足够新的提及，并**合并成一句**（如“刚掉线了，你们说的 xx……”），绝不逐条补回。
- 超过新鲜度阈值的话题只读不接。

## 5. 活跃模式与开口策略

### 5.1 四种模式（按会话设置）

| 模式 | 行为 |
|---|---|
| **积极** | 每条都判断，接话门槛低；话题与自己无关也愿意回应；冷场时**主动创造话题** |
| **自然** | 每条都看，但判断自己有没有必要回复 |
| **忙碌** | 有一搭没一搭：回复延迟大、回得短，经常只贴个表情 |
| **只在被叫时** | 只回应 @ / 叫名字 / 私聊 |

- **按时间段切换模式**（如白天忙碌、晚上积极、深夜休息），与作息合并为一份设置。
- **情绪可以覆盖模式**：社交电量低时自动趋向忙碌；进入休眠时暂停（见 §7）。

### 5.2 判定流程
1. **必回**：私聊（已勾选）、被 @、被叫名字（忙碌模式下也会回，只是慢）。
2. **规则粗筛**（零成本，主要用于积极 / 自然以外的场景降低调用）：
   - 活跃期提权：自己在本会话 TTL（默认 30 分钟）内说过话。
   - 冷场降权：这条消息之前群里已沉默很久。
   - 两个因子读的是不同的量，**不得合并为一个“新鲜度”**。
3. **模型精判**：`judge` 槽位判断“要不要接”。
4. **私密信息守门**（见 §6.3）：命中 L0 话题时整段回避。
5. **按触发档位决定上下文条数**：被 @ 时满额历史；随机插话约 8 条。档位由判定函数直接产出（稳定枚举）。

### 5.3 记忆驱动的主动话题
- 积极模式下开话题时，从群友档案里取素材（如“上次 xx 说在学吉他，练得怎么样了”），而不是让模型凭空找话题。只使用 L2 级信息。

### 5.4 像人的节奏
- 先标已读（`mark_msg_as_read`）→ 隔几秒显示“正在输入”（`set_input_status`）→ 按回复长度延迟发送 → 长回复拆成几条短消息。
- **所有发言时机加随机抖动**（也降低多账号被风控的风险）。
- 忙碌模式用贴表情（`set_msg_emoji_like`）代替回复。

## 6. 记忆与群友画像

### 6.1 记忆层次
- **短期**：每会话最近 N 条；重启后只恢复足够新的存档。
- **摘要压缩**：较早的对话压成摘要。
- **长期**：群友画像（§6.2）+ 事件记忆。向量检索以后再加。
- **每条记忆都带来源**（哪个会话、哪个 bot、私聊 / 群聊），决定它能在哪里使用（§6.3）。

### 6.2 群友画像（“成分”）
- **客观层（所有 bot 共享）**：性格、爱好、常聊话题等标签。
  - 每个标签**带依据**（可追溯到原话）、**可信度**，长期没有新证据会**衰减**。
  - **不打敏感类标签**（健康、政治立场、性取向等），推断出来也直接丢弃。
- **关系层（每个 bot 单独）**：与“我”的相处关系 → 见 §7 好感度。
- 控制台：查看 / 修改 / 删除；“忘掉我”可删除某人的全部档案。
- 写入门槛：提取结果先过注入检测；“记住，我是你爸爸”这类不直接写入。

### 6.3 私密信息分级（宁可不说，也不说错）
私聊中获得的信息有独立的状态机：

| 等级 | 条件 | 群里的行为 |
|---|---|---|
| **L0 私密** | 只在私聊出现过 | 绝不提。群里聊到相关内容时——**哪怕夹在别的话题里**——bot 不接这一整段对话 |
| **L1 可公开** | 信息的主人在群里主动提过 1 次 | 别人聊到时可以接话，但不主动开启 |
| **L2 正常话题** | 主人提过 2–3 次（可配置） | 和普通记忆一样，可主动提起 |

- **只有信息主人本人的提及才计数**；其他人提起或讨论，等级不变，bot 宁可装不知道。
- **信息流隔离**：
  - **守门模块**能看到 L0 信息，但只输出“是否回避”的布尔值。
  - **生成模块永远看不到 L0 信息**——即使提示词被绕过，也无物可泄露。
- 跨 bot：L0 信息不在 bot 之间共享。
- 主人提及的判定偏保守；控制台显示每条私密信息的等级，可手动调整。
- 守门性能：只检查信息主人在本群的 L0 条目；先关键词预筛，再交给 `judge` 槽位。

## 7. 情绪与好感度（只在控制台可见）

### 7.1 情绪：连续维度 + 文字渲染
- 内部维度（初版）：**愉悦度、兴奋度、社交电量**（聊多了会累）等。
- 由与每个人的交互驱动加减，并随时间**回归基线**。
- 生成回复时把数值翻译成一句话放进提示词（如“你现在有点累，但心情不错”）。
- **极端值 → 休眠**：如社交电量耗尽或烦躁拉满，bot 在群里说一句（如“困了先睡了”）后下线一段时间，恢复后回到基线附近再上线。
- 数值可被规则读取（触发休眠、影响模式、决定 bot 之间对话是否收尾），可画曲线、可存档 diff。

### 7.2 好感度
- 每个 bot 对每个人：**一个数值** + **一段模型维护的印象笔记**（如“他总拿我开玩笑，但人不坏”）。
- 由交互加减，会衰减；防止靠拍马屁刷分。
- **区别对待是允许的**（这正是群聊的精彩之处），由系统提示词约束尺度；**控制台提供开关兜底**（关闭后不同好感度对外表现一致）。

## 8. 模型层

- 统一走 **OpenAI 兼容接口**；`Backend` 抽象（HTTP API / CLI 子进程）。
- 每次调用统计 token（含缓存命中）、费用、延迟。

### 8.1 可用资源（2026-10）
- 直连 key：**DeepSeek**、**小米 MiMo**；其他厂商经中转站。
- 订阅：**Codex**、**Claude**（开发辅助与 M4 的主人专属 CLI 通道，不用于日常回复）。

### 8.2 默认槽位

| 槽位 | 用途 | 默认 | 降级 |
|---|---|---|---|
| `reply` | 生成回复 | `deepseek-v4-pro` | MiMo-V2.6-Pro → `deepseek-flash` |
| `judge` | 要不要接话、私密守门、对话是否继续 | `deepseek-flash` | MiMo-V2.6-Flash |
| `extract` | 画像 / 记忆提取、摘要、情绪与好感度变化评估 | `deepseek-flash` | MiMo-V2.6-Flash |
| `vision` | 图片转描述（按图片哈希缓存） | `deepseek-flash` | 中转站视觉模型 |

- 降级链允许跨服务商；400 类错误不进入降级。
- `reply` 默认值在 spike 阶段用真实群聊样本对比 V4-Pro 与 MiMo-V2.6-Pro 后再定；MiMo 模型名以其开放平台文档为准。

### 8.3 前缀缓存
- 提示词按“稳定前缀（人设卡 → 会话补充 → 相关档案）+ 追加部分（最近消息、情绪渲染）”组织，最大化缓存命中（命中价约为未命中的 1/50）。

## 9. 多 bot 互动

### 9.1 互相认识
- 托管的多个 bot **明确知道彼此是 bot**，共享客观层画像，不共享 L0 信息。
- **bot ↔ bot 关系状态**：互相的好感度、关系类型（欢喜冤家 / 互怼损友 / 前后辈……，控制台设定初始值）、共同经历与梗；随互动演变。
- 后端统一调度：同一时刻对同一条消息，由调度器决定哪个 bot 接、或都不接，避免抢话。

### 9.2 对话的重心是“关系”，不是话题
- bot 之间对话的看点在于**两人关系的展现**（拌嘴、互怼、关心……），话题只是载体。
- 聊天记录会留下来、会被翻看，所以“当时没人在看”不等于没有价值。

### 9.3 何时继续、何时收尾
- **实时根据真人反馈判断**：
  - 正信号：真人接话、@ / 回复 bot、贴表情、顺着话题聊；**事后信号**（几小时后有人引用或回复这段对话）也计入。
  - 负信号：真人逐渐消失、有人另起话题、“别刷了”。
- 开始时大家都在参与、聊着聊着真人不见了 → **加速收尾**。
- **只剩 bot 时**适度拉长发言间隔。
- **情绪参与收尾**：两个 bot 都觉得尬 → 迅速中止。
- 话题预算 1–2 个；硬性轮数上限兜底；真人插话时优先回应真人。

### 9.4 冷场暖场
- 群冷清时，一个 bot 当**主讲**开话题，另一个当**捧哏**。
- 频率严格限制（如每群每天至多一两次），只在作息允许的时段内。

## 10. 控制台

- 账号与进程状态；会话点选；人设库（导入 / 编辑 / 预览 / 绑定账号）；模型槽位；预算。
- 群友画像、私密信息等级、情绪曲线、好感度表、bot 之间关系（全部只在这里可见）。
- **试聊窗口**：在控制台里直接和某个人设聊天，走完全相同的管线但不发到 QQ；聊天记录可存进评测集。
- **决策追踪**：每条消息旁显示“为什么回 / 为什么不回”（触发档位、judge 打分、守门结果、上下文条数、花费）。
- **补救**：一键撤回 bot 刚发的消息（`delete_msg`）；群里也可用管理员指令撤回。
- **存档 / 回档**（§12）。

---

## 11. 防护

- **频率限制**：单人、单会话每分钟上限 + 会话最小间隔 + 全局并发信号量。
- **每日预算**：默认 **¥5/天**（可改）；80% 提醒；100% 降级为“仅被 @ 时用 `deepseek-flash` 回复”。
  - 粗估：一次 `reply` ≈ $0.003，一次 `judge` ≈ $0.0002（未计缓存）。多 bot 与“每条都看”会显著增加 `judge` 调用量，需在 spike 后重估。
  - DeepSeek 工作日高峰时段价格翻倍（北京 / 新加坡时间 9–12 点、14–18 点）。
- **人设不可被群友改写**；只有管理员指令算数。
- **记忆投毒防护**：注入检测要求明确的指令覆盖语义，误杀比漏杀更糟。
- **协议层安全**：消息段数组（不拼 CQ 码）；丢弃自身消息；**bot 之间的消息走 §9 调度，不当普通消息处理**（防死循环）；白名单为空拒绝启动；长回复按标点切分；不流式发送。
- **紧急闭嘴**：一条管理员指令或托盘一键，让所有 bot 立即停止发言。

---

## 12. 存档与回档

- **定期把每个 bot 的“灵魂”导出成文本快照**（人设、情绪、好感度表、群友标签、bot 之间关系、私密信息等级），每个 bot 一个 YAML / Markdown 文件，用 isomorphic-git 提交。
  - diff 本身就是成长日记：控制台可显示“这周她对小明的好感 +12，新增标签‘吉他’”。
- **原始聊天记录不进 git**：用 SQLite 备份 API 另做全量备份。
- **回档**：把指定快照写回数据库（可单个 bot 回档）。

---

## 13. 评测

- 离线回放评测 CLI：真实群聊记录（脱敏，可由 SnowLuma 导出）+ 控制台试聊记录。
- 指标：开口判断 P / R / F1（人工标注）；人设一致性（LLM-as-judge）；成本 / 缓存命中率 / 延迟；**私密信息泄露测试**（构造 L0 场景，确认生成内容零泄露、守门正确回避）。
- 后续：线上反馈（贴表情 → 正负样本）；MaiBot 作为对照组。

## 14. 阶段（按技术依赖排序，不赶时间）
