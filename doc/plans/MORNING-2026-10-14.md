## 遇到的错误
- `node --test test/tray-assets.test.ts` 首轮按预期 RED：缺少 `assets/tray/teal.ico`；创建 ICO 后同一测试通过。
- `node --test test/tray-spike.test.ts` 首轮按预期 RED：`src/spike/tray.ts` 尚不存在；实现后 4 项定向测试通过。
- 首轮 `npm run typecheck` 报 Tray 构造器类型不兼容及 `path.fileURLToPath` 不存在；改用包导出的类型，并从 `node:url` 导入 `fileURLToPath` 后通过。
- 新增 helper 意外关闭回归测试时先按预期 RED（unexpected close 被当作正常退出）；关闭路径现区分用户请求退出与 helper 异常退出，定向测试转绿。
- T12b 首轮 watcher 测试发现并发 `start()` 会建立两个计时器，且停止期间等待中的 probe 仍可能继续发 load；增加 single-flight 与 stop gate 后定向测试通过。
- T12b host 状态晚订阅无法读到当前状态，且 watcher 初始化失败时会遗留已启动的 SnowLuma 子进程；改为订阅即 read-back 状态并在启动失败时执行 stop，fake 生命周期测试通过。
- T12b 独立复核发现两个逻辑风险：fetch 默认 redirect 可能重放登录密码，二次 401 被 watcher 当成普通错误吞掉；WebUI 请求现设置 `redirect: 'error'`，终态 401 会将 host 置为 `error` 并停止扫描；回归测试与完整 `npm run check`（174 项）通过。
- 后续复核发现首次 WebUI 就绪前 SnowLuma 意外退出时，host 的通用启动清理会取消 process manager 已安排的退避重启；host 现保留可恢复重启并保持 `starting`，fake integration test 验证重试后进入等待态。
- 同次复核确认 SnowLuma 对无可探测身份的进程可返回 `{ port: 0, uin: '', identityKnown: false }`；WebUI parser 现只允许在 `identityKnown=false` 时接受端口 0，定向测试通过。
- 复核发现 runtime 声明 `webuiHost=0.0.0.0` 时仅将客户端目标改成 loopback 并不能收紧 SnowLuma 监听；WebUI client 现拒绝 wildcard/远端地址，确保托管子进程启动前 fail-closed；fake 测试验证 spawn/fetch 均未调用。
- 复核发现原请求超时只覆盖 fetch headers、不覆盖 JSON body；timeout 现持续到 body 解析完成，并以 stalled-body fake regression 验证 abort 和可重试错误。
- 复核发现进程在 watcher 首次扫描期间重启会复用旧 start promise，导致轮询计时器没有恢复；host 现等待旧扫描收束后重新启动 watcher；fake integration test 验证重启后持续轮询。
- WebUI 收到 401 或其它非 2xx 后会释放计时器但不消费响应 body；现在释放前取消未读取 body，fake stream 测试验证 401 和最终 403 两条路径。
- autostart 复核指出 install/uninstall 可能覆盖或删除同名用户脚本；VBS 现含所有权标记，操作只更新/删除本程序的普通文件；临时目录 fixture 覆盖保护与回收路径，未执行真实 Startup 安装。
- 最终复核发现 SnowLuma 环境变量可以覆盖 `runtime.json` 中的 auto-load 和 WebUI 监听设置；host spawn 现清理这些继承 override、强制 auto-load=false 和已校验的 loopback host/port/TLS，并不向子进程传递 Aquarium WebUI 密码；fake spawn 使用 hostile env 回归验证。
- 最终复核还指出 Node env-proxy 可让全局 fetch 把认证流量发给代理；客户端每次请求读取当前 global agent，可在 client 创建后动态启用 `setGlobalProxyFromEnv()` 时 fail-closed；回归通过，另有 unmanaged attach 警告与已知危险环境拒绝测试。
- 最终复核发现 SIGINT/SIGTERM 可能在 `bootstrapHost()` 等待 host.start 时到达，导致 shutdown 看不到 host，随后启动流程仍继续创建 adapter。现在 host 在 start 前登记、shutdown 先停止 host，adapter/panel 启动受 shutdown gate 控制；延迟启动回归验证 host、watcher 与后续 adapter 均不会在关闭后启动。
